# Synthesis Engine: Generalized JSON & AI Training Data Implementation Plan

This document outlines the architectural changes and implementation steps required to adapt Synthesizer's generation engine to support **Generalized JSON Template Generation** and **Grounded AI Training Data Extraction**.

## 1. High-Level Objectives

1. **JSON Template Engine**: Move beyond flat tabular data by allowing users to upload a complex JSON template and specify which arrays the AI should populate, preserving global static properties.
2. **Exhaustive Chunking Strategy (RAG)**: Extract dense, grounded training data (Q&A, instruction-tuning) from imported documents sequentially by chunk, avoiding forced constraints or hallucinations.
3. **Adaptive Dataset Sizing**: Allow semantic uniqueness decline to naturally determine when a dataset has been exhaustively generated.

---

## 2. Core Architectural Changes

### 2.1 The `JSONTemplateGenerator`

A new subsystem will be built inside `core/` to handle template parsing and injection.

* **Template Parsing**:
  * Users provide a JSON template (e.g., `thalora_data.json`).
  * The user specifies the "Target Array Path" (e.g., `nodes`).
  * The engine infers the schema of a *single item* within that array based on the first item found, or falls back to an LLM-inferred Pydantic model.
* **Agent Modification**:
  * The `row_agent.py` logic will be adapted into a `json_agent.py`.
  * The agent will be instructed to output valid JSON matching the inferred schema for a single array item.
* **Output Injection**:
  * The newly generated and validated JSON object is appended to the target array in memory.
  * Once generation stops, the entire master JSON structure (including static data like global configs or contexts) is exported.

### 2.2 Exhaustive Chunking RAG Pipeline

This replaces the current prompt-first RAG approach with a chunk-first approach for training data.

* **Chunk Iterator**:
  * When a user imports a document and enters "Training Data Mode", the engine accesses the `RagService` to fetch **all** semantic chunks of the document sequentially.
* **Density-Aware Prompting**:
  * The AI is fed one chunk at a time.
  * *Prompt structure*: "Analyze this specific chunk of text. Extract as many discrete, factual training pairs (Instruction/Response) as this text naturally supports. Do not hallucinate. If the text contains no actionable training data, return an empty array."
* **Elimination of Target Row Counts**:
  * The generation loop completes precisely when all document chunks have been processed. The final dataset size is determined by the document's density, ensuring 100% data grounding.

### 2.3 Semantic Validation for Nested Objects

The existing `UniquenessValidator` needs an upgrade to handle unstructured dicts using **Path-Based Flattening**.

* **Path-Based Extraction**: Before validation, a nested JSON object generated by the AI is passed through a recursive string extractor (`extract_strings_for_hashing(obj: dict)`). Instead of just values, it constructs complete "path: value" strings (e.g., `user.data.status_code: 500`).
* **Concatenated Embedding**: The path-aware strings are passed into the `sentence-transformers` embedding model. This captures both the value and its functional role within the schema.
* **Tiered Deduplication**: Include an initial layer of exact hash deduplication (SHA-256) before Semantic DBSCAN clustering or dense vector comparisons. Thresholds typically require tuning to 0.85-0.95 within semantic clusters.

## 3. Implementation Steps

### Phase 1: Generalized JSON Templating (Backend)

* [x] **Create `core/json_parser.py`**: Add utilities for reading a template JSON, removing existing target array data, and formulating a Pydantic schema based on array item structure.

* [x] **Create `core/json_agent.py`**: Adapt the LangGraph state machine. Change the prompt to strictly require JSON output matching the inferred schema of the target array object.
* [x] **Update `core/validator.py`**: Implement `extract_strings_for_hashing` to recursively pull out relevant text fields from a generated JSON dict for semantic validation.
* [x] **Modify `GeneratorController`**: Add a `generate_json_batch` loop that iterates the `json_agent.py`, validates the result, and injects it back into the master template.

### Phase 2: Exhaustive Document Extraction (RAG)

* [x] **Update `core/rag/service.py`**: Add a method `get_all_chunks(source_filter=None)` to bypass search and just return the raw text chunks sequentially.

* [x] **Create `core/chunk_agent.py`**: A specialized zero-shot extraction agent that uses "Self-Foveate" and "Chain-of-Verification (CoVe)" prompting. It takes a raw text chunk and outputs an array of factual, strictly grounded pairs without hallucinations.
* [x] **Implement Critique & Filter Stage**: Add a strict secondary "LLM-as-a-Judge" step inside the controller to verify that a generated QA pair is implicitly located in the source chunk text.
* [x] **Integrate into Loop**: Update the `GeneratorController` so that if "Exhaustive Mode" is selected, the loop's length is `len(total_chunks)`, not a hardcoded target list.

### Phase 3: GUI Integration

* [x] **Create Files workspace JSON template controls**: The `Work With Files` tab now exposes JSON template selection directly in the main layout instead of a separate `json_template_picker.py` control.

* [x] **UI State Updates**: Users can define a "Target Key" (for example `nodes` or `data.messages`) in Files -> Structured JSON mode.
* [x] **Mode Toggle**: Files -> Structured JSON includes `Standard Generation` vs `Exhaustive Extraction`.
* [ ] **Progress Updates**: Exhaustive mode currently updates shared progress/logging, but does not yet show a dedicated `Chunks Processed: 12/50` label in the Files UI.

## 4. Risks and Mitigations

* **Risk**: The AI fails to adhere strictly to the nested JSON schema of the target array, causing JSON decoding errors.
  * **Mitigation**: Move from LLM retry-based Structured Output to **Constrained Decoding**. Dynamically convert the target template object into a Pydantic `BaseModel` at runtime, and utilize a structured generation library like **Outlines** (which converts Pydantic to a mask-enforcing FSM). If the template requires arbitrary recursion, upgrade the constraint engine to a Context-Free Grammar (CFG) engine like XGrammar or the `llama.cpp` GBNF engine.
* **Risk**: Exhaustive chunking generates extremely redundant instructions from overlapping RAG chunks or hallucinated responses from sparse chunks.
  * **Mitigation**: The `UniquenessValidator` is run on *every* extracted pair using Path-Based Flattening to instantly reject duplicates. To stop hallucinations, enforce the secondary "LLM-as-a-Judge" Critique and Filter stage on every new inference generation.
* **Risk**: Template parsing fails because the target array is deeply nested (e.g., `app_state.user.history.messages`).
  * **Mitigation**: Implement standard dot-notation parsing (like `pydash` or `jmespath`) allowing users to easily target `user.history.messages` in the UI.

---

*This plan represents a formal architecture shift from "Flat Row Data Synthesis" to "Hierarchical JSON & Knowledge Extraction Synthesis."*
